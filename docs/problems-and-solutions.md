# 问题解决记录

本文记录开发过程中实际遇到的关键问题、根因与解决方案。

## 1. 级别检测正则失效（级别全部显示 UNKNOWN）

**现象**：日志查看器中所有行的级别都显示 `UNKNOWN`，但行内明明有 `INFO` / `DEBUG`。

**根因**：级别匹配正则 `/(?:^|[[\]\s:\-=,|]).../` 中，把字面量 `[`、`]` 直接放在字符类开头/结尾，JavaScript 对「字符类首个 `]`」的解析与预期不符，导致边界字符类失效，` INFO ` 这种「前后都是空格」的匹配失败。

**解决**：改为把 `[`、`]` 转义后放在字符类末尾 `[\s:\-=,|\[\]]`，并移除误加的 `\b`（`\b` 会导致 `INFO: ` 这类「后接非词字符」的场景失配）。用一组真实格式样例回归验证通过。

**教训**：字符类内的 `[` `]` 统一转义并放末尾，是最不容易出错、可读性最好的写法。

## 2. 全进程内存读数异常偏低（totalRssMB ≈ 0.4MB）

**现象**：内存面板里「全进程」只有 0.4MB，明显错误。

**根因**：`app.getAppMetrics()` 返回的 `memory.workingSetSize` 单位是 **KB**，而代码按字节（`/1024/1024`）换算，小了 1024 倍。

**解决**：KB→MB 用 `/1024`，字节→MB 用 `/1024/1024`，两套换算分开。修复后全进程读数恢复正常（~360MB）。

**教训**：跨 API 传数据时，单位必须查文档确认，不能想当然。

## 3. 虚拟滚动无法访问文件深处行（2GB 文件只能滚到 ~167 万行）

**现象**：2390 万行 × 20px = 4.78 亿 px 的滚动高度，导致只能滚到约 167 万行，之后无法继续。

**根因**：Chromium 的 `scrollTop` 上限约 **3350 万 px**（`2^25 - 1`）。直接按「行数 × 行高」布局超大列表，总高度超过浏览器上限，超出部分不可达。

**解决**：改用「虚拟滚动条 + 粘性视窗」：
- 滚动范围固定为 3000 万 px（低于浏览器上限）
- 由滚动位置按比例映射到起始行号 `startLine = floor(scrollTop / scrollH * totalLines)`
- 只渲染可见的几十行到 `position: sticky` 容器
- 小文件则退回精确逐行滚动

**效果**：任意一行可访问（验证滚动到第 18,177,361 行），滚动平滑。

**教训**：浏览器对滚动偏移有硬上限，超大列表不能直接按行数撑高容器。

## 4. 渲染进程原生内存异常膨胀（~608MB）

**现象**：打开 2GB 文件后，渲染进程（Tab）`workingSetSize` 从 ~115MB 涨到 ~608MB，但 JS 堆只有 21.7MB、DOM 节点仅 ~450 个。

**排查**：通过对比「截图前/后」内存，排除 `capturePage` 截图的临时开销；通过注入 `performance.memory` 确认 JS 堆无泄漏。

**根因**：问题 3 中 4.78 亿 px 的超大滚动布局，Chromium 为维护这个巨大的滚动区域分配了大量原生内存。

**解决**：随问题 3 一并修复。改用 3000 万 px 虚拟滚动条后，渲染进程原生内存降至 ~350MB。

**教训**：`workingSetSize` 与 JS 堆是两个概念。排查「内存高」要先分清是 JS 堆泄漏（代码问题）还是原生/布局开销（结构问题）。

## 5. 错误聚类被服务名 / 数字拆散

**现象**：同一类错误（如「数据库连接失败」）按不同服务名（user-service/payment-service/...）被拆成 5 条，每条 ~750 次，而非聚合成一条 ~3800 次；`1439ms` 这类数字也未归一化。

**根因**：
1. 提取错误消息时只剥离了行首 `[时间戳]`，保留了 `com.example.xxx - ` 日志器前缀
2. 数字归一化用 `\b\d+\b`，「数字后紧接字母」时（如 `1439ms`）`\b` 不成立，数字被漏掉

**解决**：
1. 消息提取时额外剥离 `级别 + 日志器前缀`
2. 数字归一化改为 `/\d+/g`，覆盖「数字+字母」场景

**效果**：120 万条错误折叠成 16 个签名，Top 集群每条 ~15 万次。

**教训**：聚类质量取决于签名归一化是否彻底；`\b` 在「字母-数字」相邻处不构成边界。

## 6. 索引期间 UI 响应性

**现象/风险**：2GB 文件索引需扫描全部字节，若在主进程同步循环会阻塞事件循环，导致窗口与 IPC 卡死。

**解决**：分块读取 + 每块之间 `setImmediate` 让出事件循环，索引/搜索/统计共用这一模式。实测 2GB 索引 ~20s、全量搜索 ~7s、统计流畅完成，期间 UI 可交互、可取消。

## 总结

本次开发中遇到的问题集中在三类：
1. **正则边界语义**（问题 1、5）——字符类与 `\b` 的边界行为
2. **单位/换算错误**（问题 2）——跨 API 数据单位
3. **浏览器底层限制**（问题 3、4）——滚动偏移上限及其连锁内存开销

它们都通过「现象 → 根因 → 最小复现 → 修复 → 回归验证」的路径解决，并沉淀为文档与代码注释。
